# AI 协作开发过程

> 本项目从需求到可用原型，全程由 **AI Agent 与人类协作**完成。这份文档如实记录工作方式、验证纪律，以及**踩过的每一个坑**——因为踩坑记录比"最终代码"更有复用价值。

## 1. 工作方式

### 1.1 先调研，后动手

第一步不是写代码，而是**并行调研**（7 路独立调查同时进行）：

- 目标硬件/系统的真实约束（触控技术、笔协议、系统版本、部署方式）
- 开源生态里有没有现成可复用/可 fork 的项目
- 技术栈的内存与性能实测数据
- 引擎（PDFium / MuPDF / pdf.js）与画布库的取舍
- 多文档与视口渲染的内存架构
- 同类软件的功能对标（用于圈定 MVP 边界）

结论先落成**带证据的文档**（见 `01-技术选型与调研.md`），再决定架构。

### 1.2 计划先过"对抗性评审"

技术方案写成计划文档后，交给一个**专门唱反调**的评审角色检查：引用是否可核验、是否可执行、验收标准是否可判定。评审结论是"无阻塞，可执行"后才进入实现。

### 1.3 里程碑 + 每步可验证

不做"一次写完再测"，而是**小步 + 每步可测**：

| 阶段 | 产出 | 验证方式 |
|---|---|---|
| M0 | 打开一页、画一笔 | 目标机实测内存与耗时 |
| M1 | 连续滚动 + 视口渲染 | 滚动流畅度 + 内存 |
| M2 | 墨迹 + 橡皮 + 触控 | 真机书写/擦除/双指 |
| M3 | 多文档标签 | 切换正确性 + 内存 |
| M4 | `.dpz` 保存 / 注入 PDF | 端到端往返 |
| M5 | 界面与体验 | 观感与触控目标 |

### 1.4 验证纪律（最重要的一条）

1. **编译器零警告**（MSVC `/W4`）——所有改动都必须做到。
2. **确定性自测**：`--selftest-ink` 用程序直接驱动墨迹模型（不依赖鼠标），断言"画→局部擦→撤销→重做→缩放→笔迹粗细"等 30+ 项。**它是本项目抓到最多真 bug 的工具**，因为很多问题在"点几下"的测试里根本复现不出来。
3. **真机验证**：所有交互类改动都在带触摸屏的真实环境里跑一遍，截图留证。
4. **不盲信 Agent 的输出**：多次出现"Agent 汇报完成、磁盘上却没有文件"（它只输出了计划）。因此每次委托后都要**独立核对文件是否存在、构建是否通过、自测是否全绿**，再继续。

## 2. 踩坑记录（现象 → 根因 → 修复）

### 渲染与视觉

**2.1 页面底色透明**
- 现象：PDF 页空白处透出窗口深色背景。
- 根因：PDF 页本身没有背景色，渲染返回的位图带 alpha 通道。
- 修复：绘制页面时先在页面矩形内填充纸白（比再开一张缓冲更省内存）。

**2.2 底部工具岛被任务栏挡住**
- 现象：窗口默认高度超出"工作区"，底部控件被任务栏覆盖。
- 修复：窗口尺寸改为按 `availableGeometry()`（排除任务栏）计算并居中。

**2.3 浮层出现一圈"方形阴影"**
- 现象：笔调色板是圆角卡片，但外面套着一个**方方正正**的阴影。
- 根因：调色板是**无边框顶层窗口**，系统会给它加一圈按**窗口矩形**计算的原生阴影。
- 修复：改为**视口内的子控件浮层**（不是窗口 → 没有原生阴影），只保留卡片自己的圆角软阴影。

**2.4 启动时浮层自动弹出**
- 现象：程序一启动，调色板就是打开的。
- 根因：**从未显式隐藏过的子控件，会随父控件一起显示**。
- 修复：创建后显式 `hide()`。

### 输入与手势

**2.5 点浮层会被"判成别的东西"然后消失**
- 现象：点调色板里的色块，调色板反而关掉了，选不中颜色。
- 根因：画布**接受触摸事件**，于是落在子控件（浮层）上的触摸，也会以"画布"的身份报给全局事件过滤器；而过滤器当时是按"事件投递给了哪个控件"来判断内外的。
- 修复：改为按**事件坐标**判断是否落在浮层内；同时画布**不再把落在浮层上的触摸当成书写**。

**2.6 双指操作时会误画**
- 现象：双指捏合/拖动时页面被画上笔迹。
- 根因（两层）：
  1. 双指落下时第一根手指已经起笔；
  2. 触摸**同时被转发为合成鼠标事件**，而最初只锁了触摸路径，鼠标路径照样完成了整笔提交。
- 修复：出现第二触点即**锁书写**（直到全部抬起并延迟 250 ms），**鼠标路径同样受锁约束**，`TouchCancel` 一律丢弃而不是提交，并过滤掉短于 3 px 的误触。

**2.7 双指只能滚动，不能缩放**
- 现象：双指操作只产生滚动，没有缩放。
- 根因：依赖 Windows 原生捏合手势，而很多红外屏/转发式触摸**不产生该手势**。
- 修复：改为**直接读取多点触摸事件**——触摸点距离算缩放比、中点位移算平移，二者同时生效。

**2.8 缩放"以左边为中心"**
- 现象：捏合缩放时视野偏向页面左边缘，不像以两指中心为锚点。
- 根因：缩放只补偿了**纵向**位置，横向没有补偿（放大后页面变宽，横向滚动值没跟着调）。
- 修复：记录"锚点下的页 + 页内横纵相对位置"，重排后**横纵都**移回锚点下。

**2.9 放大卡顿 + 内存攀升**
- 现象：捏合缩放时明显卡，内存一路上涨。
- 根因：**每次触摸事件都清空整页位图缓存**，下一帧必须同步重渲（高倍时几十到上百毫秒），同时反复创建超大位图。
- 修复：手势进行中**不清缓存**，直接把已有位图拉伸绘制（瞬时）；手势停止 160 ms 后再重渲清晰版；并给单页位图加上限。

**2.10 墨迹粗细不随缩放变化**
- 现象：放大时写的字，缩回适配宽度后线条依旧很粗。
- 根因：笔画粗细存的是**设备像素**（固定值）。
- 修复：粗细改为**按页宽比例**存储，绘制与擦除时再换算成像素。

### 橡皮与墨迹模型

**2.11 橡皮"整条删除"**
- 现象：橡皮碰到笔迹就整条消失。
- 修复：改为**局部切除**——求每段与橡皮圆的相交区间，切掉圆内部分，圆外保留（一条可被切成两段）。

**2.12 擦除后撤销，恢复的不是原状态**
- 现象：擦断一条线后按撤销，回不去原来的完整一条。
- 根因：**Qt 隐式共享 + 失效迭代器**。快照复制了墨迹容器（COW 共享同一份数据），之后又用**快照前取得的迭代器**就地改写——直接改到了共享缓冲区，把快照内容一起改成了"擦除后"的状态。绘制路径用的是会正确 detach 的写法，所以只有擦除的撤销坏了。
- 修复：快照前取值拷贝，快照后用索引重新赋值。**这个 bug 是靠新增的确定性自测抓出来的**（点几下永远测不出）。

**2.13 快速拖动擦除：要么漏擦、要么擦掉一大片**
- 现象：快速拖动时笔迹被擦成虚线；有时又一下子擦掉很长的段。
- 根因：只按指针当前位置擦，两次采样之间没有扫掠；加了扫掠后，丢事件/瞬移又会让"两点之间"被整体擦掉。
- 修复：**沿轨迹插值扫掠** + **跳跃保护**（单次位移超过阈值就只擦落点附近的窗口）。

**2.14 稀疏笔迹擦一下就整段消失**
- 现象：**快速画的线**（采样点很少）擦中间一下，右侧整段没了。
- 根因：切分笔迹时，一段"离开橡皮圆"的那一刻只补了出圆点，**漏掉了该段自己的终点**；对稀疏笔迹，出圆后那一段只剩 1 个点，被"不足两点"规则丢弃 → 整段消失。
- 修复：出圆时同时补回该段终点；并新增"稀疏笔迹"回归测试。此外**书写采样自动补密**，从源头降低这类风险。

### 文档与保存

**2.15 `.dpz` 双击/命令行打不开**
- 现象：用 `.dpz` 作为参数启动，显示空状态。
- 根因：命令行参数只接受 `.pdf` 后缀。
- 修复：同时接受 `.dpz`；并把 `.dpz` 纳入文件关联。

**2.16 另存为的预填文件名是乱码**
- 现象：切到"注入 PDF"时，默认文件名变成怪串。
- 根因：文档若由 `.dpz` 打开，其"源 PDF"是**内部临时副本**，默认名/目录取自临时文件；另外把说明文字塞进过滤器串，干扰了框架自己的后缀处理。
- 修复：取**包/PDF 的真实身份**作基名与目录；注入格式的默认名 = **源文件名 + `-已批注`**；切换格式时主动重填名字；说明文字移到"保存类型"标签上。

### 工程与合规

**2.17 误留测试脚手架**
- 冒烟测试代码一度被留在出厂的 `main.cpp` 里（还会写截图文件）。已按要求清除。

**2.18 商标清理**
- 项目早期文案/标识中出现过某硬件厂商与商业白板软件的名称。为避免商标与版权风险，**已全项目清除**（源码、文档、可执行文件名、注册表项、环境变量），产品名中性化为「大屏 PDF 批注」，可执行文件为 `pdfboard.exe`。

**2.19 诊断日志"关不掉"**
- 现象：从一个设置了 `PDFBOARD_LOG` 的终端启动后，设置页里的「写入诊断日志」开关**拨不动**——关掉立刻自己弹回开启，日志文件照写，而注册表里存的明明是 `false`。
- 根因：`AppLog::applySettings()` 把**环境变量的优先级放在了用户设置之上**（`want = 用户设置 || 环境变量非空`），变量一旦存在，开关就被锁死在"开"。设计意图是"给无法点按的机器留后门"，结果把"临时默认值"做成了"不可撤销的强制项"。
- 修复：环境变量降级为**只决定启动默认值与日志路径**，用户在设置页的点击**永远优先**（本次运行内记住"已被用户否决"）；关闭时**同时释放日志文件句柄**（不再"关了还占着文件"）；设置页会标注"本次由环境变量 PDFBOARD_LOG 指定路径"，让开关为什么一开始是开着的**有据可查**。
- 回归锁：新增 `--selftest-log`，断言「环境变量开启 → 关掉开关 → 确实不写 → 再打开 → 恢复写入 → 结束后还原用户设置」，其中"关掉开关"这一条在修复前是 FAIL。

**2.20 深色模式"改了不生效"**
- 现象：设置里选深色、启动日志也写着"设置 2 → 解析 2"，但界面（工具岛、标签栏）仍渲染亮色。
- 排查：先在启动处与**绘制期**各打一条探针，把"解析到的模式"和"绘制时真正读到的 `desk` 色值"一起写进日志。结果：启动处说深色，而画面是浅色——说明**同一份调色板在两个编译单元里不是同一个对象**。
- 根因：`Theme.h` 里调色板存成**内联函数的函数局部 static**，该工具链把它在多个编译单元复制成了多份：`main` 改写的是自己那份，真正绘制的编译单元读的是另一份（仍是浅色）。
- 修复：改成 C++17 **`inline` 变量**（标准保证全程序唯一）；修复后启动期与绘制期的调色板地址一致、`desk=27,27,31`（暗色）✓。
- 经验：**跨编译单元共享的可变状态，不要用函数局部 static。**

**2.21 暗色下设置页卡片还是白底**
- 现象：深色模式生效后（页面底色、标签栏都变暗），只有设置页的卡片仍是白的，卡片上的浅灰文字几乎看不清。
- 根因：设置页样式表把卡片背景写成 `paper`。而 `paper` 是"**PDF 纸面**"令牌，暗色下**有意保持白**（教室投影必须像纸），卡片该用的是 `surface`。
- 修复：卡片改用 `surface`，并在样式表处注释清楚 `paper` 与 `surface` 的分工，避免再踩。

**2.22 需求语义理解错了（自由移动）**
- 现象：把"纯拖动模式"实现成了"拖动工具岛"，实际需求是**拖动画面**（手型平移）。
- 修复：改为双轴 `panBy`（与双指平移同一条路径）；工具岛**自身可拖**作为独立功能保留。
- 经验：需求里出现"移动/拖动"时，先问清**移动的是谁**——一次澄清省一轮返工。

**2.23 工具岛"整体缩到 80%"不能只缩字号**
- 现象：只把工具岛字号乘 0.8，工具岛几乎没变小。
- 根因：度量值里每一项都有**地板值**（如 `touch = qMax(48, h*2.20)`），字号变小时地板值接管，宽度由最小尺寸决定。
- 修复：给 `Theme::metrics()` 加 `scale` 参数，**连地板值一起乘**，字号与度量一次到位（新增断言锁定 ~80%）。

**2.24 windows.h 的遗留宏吃掉了变量名**
- 现象：`const int far = ...`、`const QPoint small(...)` 编译报"缺少变量名/非法"。
- 根因：`windef.h`/`rpcndr.h` 至今仍定义 `far`、`near`、`small` 等宏（`#define small char`）。
- 修复：改名（`beyond` / `tinyMove`）并加注释。
- 经验：Windows 项目里别拿 `far/near/small/min/max/IN/OUT` 当标识符。

**2.25 拖动测试的假通过**
- 现象：新增的"拖动后不该点击按钮"断言一开始是 PASS，但实现其实是坏的。
- 根因：测试把释放点放在了按钮外，`QAbstractButton` 本来就不会触发 `clicked` —— **断言恒真**，等于没测。
- 修复：利用"抓点始终跟着指针"的拖动特性，让释放点仍落在按钮内，这样只有过滤器吞掉释放才会不点击；同时把工具岛先挪离钳制边界（否则它已贴在右下角，任何移动都看不出来）。
- 经验：**断言要通过"否则必然失败"的检查**——不然比没有更危险。

**2.26 触屏"采样点不足"其实是 Qt 把样本合并掉了**
- 现象：快速连笔难以辨认，**放大后更明显**（同一次误差在屏幕上被放大同样倍数）。
- 排查顺序：先查补密阈值与"直线硬连"渲染，改完仍不够 → 转向输入层。查 Qt 文档发现 `Qt::AA_CompressHighFrequencyEvents` **在 Windows 8+ 上会压缩触摸事件**：把一帧内的多个真实触点样本合并成一个事件、其余直接丢弃；而唯一能捞回被合并样本的 `QEventPoint::rawScreenPositions()` 在 **6.8.3 里根本不存在**（已核对本地头文件，不是猜的）。
- 第二个陷阱：在 `QApplication` 构造**之前** `setAttribute(..., false)` **无效**——Windows 平台集成初始化时会把它**重新打开**；必须在构造**之后**再设一次（插件按事件读取该属性）。这条用断言实测过：构造前设置 → `got 1 want 0 -> FAIL`；构造后补设 → PASS。
- 修复：`main()` 中在 `QApplication` 之后 `setAttribute(Qt::AA_CompressHighFrequencyEvents, false)`，并加断言锁死（`--selftest-ink` 的 `input: touch not compressed`）。
- 经验：**"采样不足"要先确认样本是被谁丢的** —— 很可能是框架默认行为，而不是硬件上限；另外"设置没生效"要怀疑**平台集成会覆盖**。

**2.27 每个采样都整屏重绘：采样没丢，是被自己的重绘堵住了**
- 现象：快速书写"跟不上手"、看起来像采样不足；捏合缩放只有 15~20 帧。
- 排查：先核实代码而不是猜——发现两处**纯浪费**：① `moveInputTo()` 每收到一个采样就 `viewport()->update()` **整屏**重绘（4K/DPR 2.5 下要重绘背景 + 每页 3 层阴影 + 圆角路径裁剪 + 双线性缩放的大位图）✗ ② 橡皮 `eraseAtPointer()` 同样整屏重绘，而一次 40px 抹动会走 ~7 步 ✗ ③ 缩放期间明明用的是**旧比例的模糊位图**，却开着 `SmoothPixmapTransform` 白花双线性时间 ✗
- 一个关键认知：面板每 ~8ms 送一个采样，而一次整屏重绘要几十毫秒 → **采样确实到了，但像素卡在与它无关的重绘后面**，表现出来就是"采样点不足/笔画被拉直" ✓
- 修复：新增 `src/InkDirty.h`，按"笔迹只用最后三个采样点的凸包 + 半个笔宽 + AA 余量"算出**必须重绘的视图矩形**：书写与橡皮都改成局部重绘（橡皮只刷橡皮圆），手势期间关掉 `SmoothPixmapTransform`，手指停下重渲染后再开 ✓
- 回归锁：7 条断言（脏矩形远小于视图、覆盖新旧采样、漏掉更早采样、余量生效、单采样、空输入安全）✓
- 经验：**"输入跟不上"先看每帧成本**——UI 线程一忙，输入会被队列化，症状和"采样不足"长得一模一样 ✗

**2.28 教室实测：采样从来不缺，卡在"笔落下的那一刻"**
- 数据（教室一体机真机日志）：126 ms 内 53 个 `touch type=195`，**≈420 事件/秒**，且**同一毫秒内有 2~5 个完全相同的帧**（`total=1 active=1`）→ 面板把**同一个采样重复投递了约 4 次** ✗（红外屏不可能真有 1000 Hz）。**"采样不足"的假设就此排除** ✓
- 新症状：**刚开始写会卡顿，拖一段距离后才流畅** —— 这句话直接指出"笔落下时有一次重活儿" ✓
- 根因：缩放/打开后 `invalidateRenders()` 已把页面位图缓存清空；笔一落下，第一次重绘里 `imageFor()` **在 UI 线程同步**渲染 2~4 页 4K 位图（每页几十毫秒）✗✗ → 忙完（就是"拖的那一段距离"）才恢复流畅 ✓
- 修复：① 笔落下时**取消**缩放后的"变清晰"定时器，抬笔后再启动（写字优先于变清晰）② 书写/手势期间页面按**半分辨率**栅格化（像素少 4 倍），抬笔后由同一定时器统一变清晰 ③ **丢弃重复采样**（`dist < 1e-6` 直接跳过）④ 起笔也改局部重绘
- 另一个教训：**诊断日志本身成了卡顿源** —— 420 事件/秒 × 每条同步写文件 ✗。`eraseLog()` 改为**每 250ms 最多一行**、合并计数，既去掉干扰又让日志可读 ✓
- 经验：**先量事件率，再谈"采样不足"**；以及"越写越流畅"这类**随时间改善**的症状，几乎都是**一次性重活儿**（冷缓存/同步栅格化），不是输入问题 ✓

**2.29 缩略图在深色模式下没有白底**
- 现象：页面切换浮层（PageGrid）里每个页面的白底消失（浅色模式下看不出来，一直没暴露）。

**2.30 发版必须带更新日志**

- 现象：应用现在会在启动 / 打开文件时查询最新 Release，把它的 body 以纯文本显示在「发现新版本」对话框和设置页的更新区；可某次发版的说明是空的，老师那边点开只看到一片空白 ✗
- 根因：workflow 之前把「发布说明」硬编码在 `release.yml` 的 `body:` 里，与标签注解各写各的；改成读取标签注解后又发现，`git tag vX`（轻量标签）根本没有注解，而 Windows PowerShell 直接 `-m "多行…"` 会把换行弄坏，tag message 就残缺甚至为空 ✗

- 经验：**面向用户的更新日志要跟着版本一起走**——写进标签注解，发版即发布说明；否则代码发了、说明忘了，用户端只会收到一条空通知 ✓

**2.31 笔迹写到工具岛上就整条消失**
- 现象：从页面起笔、写进底部工具岛，**整条笔迹（连上岛之前那段）都消失** ✗
- 根因：`handleTouch()` 在**每一帧**都做一次"落点在浮层上就拦截"；被拦截即 `m_touchInkBlocked = true`，而 `endInput()` 见到这个锁会 **`cancelGesture()` 丢掉整条笔迹** ✗✗ —— 一个"别在浮层下面起笔"的保护，被写成了"整条作废" ✓
- 修复：抽出 `touchBelongsToOverlay()`：**只有"准备开始"的触摸**才交给浮层；进行中的书写/橡皮/捏合/平移**一律继续收样本** → 笔迹继续 ✓（浮层是 viewport 的子控件，被盖住的那段就等于"写在岛下" ✓ 正是需求 ✓）；在岛上**起手**拖动依旧是移动工具岛 ✓
- 回归锁：5 条断言，其中 `overlay: ink survives the island` 在修复前必然 FAIL（笔迹被取消 → strokeCount 0）✓
- 两次踩坑：① 断言块最初用主画布，`beginInputAt/endInput` 会推撤销快照，**污染了后面 4 条老断言** ✗ → 改用**独立画布**做该测试 ✓ ② `eraseLog()` 改写时多了一个 `}`，把匿名 namespace 提前闭合（好在编译立刻报错 ✓）
- 经验：**"拦截"和"作废"是两件事**——保护性拦截绝不能顺手丢掉已有结果；测试也要注意副作用隔离 ✓

**2.32 图片导入与 PNG 导出：两个"想当然"的坑 + 一条数据和命名的规矩**
- 需求：图片要能像 PDF 一样批注/保存/导出；PNG 导出按"原页面等像素"**1:1**；多页导出多张，序号按页数补零。
- 设计取巧（正向）：图片没有"页"，于是把图片按**原像素**包成一页 PDF（页面 = 像素 × 72/96 pt ✓）→ 现有全部能力（缩放/批注/`.dpz`/注入 PDF/导出）**零改动可用** ✓；导出时按 96 DPI 渲染正好回到原像素 = **严格 1:1** ✓（复用比新建强：省掉一整套图片文档后端 ✓）
- 坑一：`qCompress()` 的输出**不是**裸 zlib 流，前面有 **4 字节大端长度头** ✗，而 PDF 的 `/Filter /FlateDecode` 要的是裸 zlib → 必须 `qCompress(raw).mid(4)` ✓（否则阅读器白页/报错）
- 坑二：`/DeviceRGB` 的字节序（RGB vs BGR）网上说法不一 ✗ —— **不靠记忆，靠回环断言定案**：造 800×600 四象限图 → 转 PDF → 打开 → 导出 PNG → 断言**四象限颜色 + 四边黑框**都还在 ✓；顺序一颠倒断言必挂 ✓（结论：RGB 正确 ✓）
- 坑三（数据安全）：导出目标是"基名+序号"，若老师的原图恰好叫 `img-1.png`，导出基名 `img` 就会**把原图覆盖掉** ✗ → 导出前把每个目标路径与 源图/源 PDF/.dpz 逐个比对，命中即拒绝并提示 ✓
- 坑四（UX 语义）：导出 **不等于** 保存 —— 导出 PNG 后**不**标记"已保存" ✓，`.dpz` 没写就仍然标脏 ✓ 否则关窗时老师会以为批注已存好 ✗
- 回归锁：`--selftest-image` 共 36 条断言（含 1:1 回环 11 条、超限降采样 2 条、命名规则 4 条）✓；两个 CI workflow 的门禁从"只跑 `--selftest-log`"扩成 **7 个无参自测循环**（任一非 0 即失败）✓
- 经验：**能"包一层"就别"新写一条后端"** ✓；**字节序/编码这类无法从记忆确定的细节，用一条必然会失败的断言定案** ✓

**2.34 没有触摸屏就没法缩放：滚轮 + 快捷键 + 状态栏缩放条**
- 现象（用户报）：教室一体机之外的机器（没有触摸屏）**完全没法缩放** ✗
- 根因两条：① 完全没有缩放快捷键 ✗（只有 Ctrl+O/T/W/S ✓）② 只有双指捏合这一条缩放途径 ✗

- 实现：`Ctrl+滚轮` 缩放（锚在光标 ✓ 25%~400% ✓ 每格 ×1.25 ✓）；**普通滚轮照旧滚动** ✓；`Ctrl+=` / `Ctrl+-` / `Ctrl+0`（适配宽度）✓；状态栏最右加 Word 式缩放条 `[−] ▬▬▬ [+] 120%`（**只在文档页显示** ✓ 拖动滑块/±按钮/点百分号回适配宽度 ✓）
- 双保险（针对"面板把双指滑动报成滚轮"）：`handleWheel()` 在**触摸手势进行中 + 结束后 250ms 内吞掉一切滚轮** ✓（连滚动都不做 ✓），被忽略时写日志 ✓ —— 就算某型号面板真这么干，日志能指认它 ✓
- 断言：`--selftest-ink` 新增 15 条（真发 `QWheelEvent` 走生产路径 ✓：Ctrl+滚轮会缩放 ✓ / 普通滚轮**不**缩放 ✓ / 手势进行中忽略 ✓ / 抬笔 250ms 内仍忽略 ✓）+ 缩放条映射 6 条（5 点 + 往返 ✓）
- 两次踩坑：① `testWheelAt` 忘了 `#include <QApplication>` → 编译失败 ✓ ② `testTouchEnd()` 直接调 `endInput()` **绕过了真实触摸路径的 250ms 尾随锁** ✗，导致"抬笔后仍忽略"这条**假失败** → 把钩子改成与真实路径一致（begin 停锁 / end 起锁）✓
- 经验：**"拦截"要区分"开始"与"进行中"** ✓；**测试钩子必须忠实复刻生产路径**，否则测的不是真东西 ✓

**2.42 栈溢出的真机制：绘制路径里改 UI（"paint → 同步 flush → paint"自递归）**
- 现象：1.8.2 / 1.8.3 仍复发 `0xC00000FD` ✓，崩溃偏移是 **`Qt6Widgets.dll+0xD4DBF`**（与 2.41 那条 `+0x333DB` **不同** ✓）；面包屑一串 `zoom` ✓ 且**没有 `zoom-reentry`** ✓ **也没有 `render-nested`** ✓
- 破案方法（这次真正走通的路子 ✓）：用户把 **8.5 MB 的 minidump** 拷出来 ✓ → 我**自写 minidump 解析器**（Python，无任何符号）✓ 扫崩溃线程栈上的代码指针 ✓✓ → 看出**每 2216 次重复**、**每周期 43 帧 / 2832 字节栈**的稳定周期 ✓✓ → 再用 **`.pdata` 运行时函数表**精确定位每个 RVA 属于哪个函数 ✓ + **校验本机 Qt DLL 与 VM 那份逐字节同源**（`TimeDateStamp`+`SizeOfImage` ✓ `0x67d82e05`/`0x634000` ✓✓）→ 最后读函数引用的**字符串字面量**给帧命名 ✓✓
- 认出的周期：**`QMetaObject::activate`（每周期 2 次）+ `sendThroughObjectEventFilters` + `QWidgetRepaintManager::markDirty` + `QWidget::mapTo` + `user32`（`RedrawWindow` 同步喷）+ `qwindows!windowsProc`** ✓✓ = **"绘制中触发同步重绘 → `paintEvent` 自递归"** ✓✓✓
- 根因：`PdfCanvas::imageFor()`（由 `paintEvent` 调用 ✓）里**直接 `emit renderMeasured` → 状态栏 `m_renderLabel->setText`** ✓✓ → **在绘制期间改了 UI** ✓ → Qt 把该区域标脏并**立刻 flush** ✓ → 再次进入 `paintEvent` ✓ → 再次 `imageFor`（缓存已命中 ✓ 所以每层极快 ✓）→ **递归到 8 MB 栈耗尽** ✓✓✓（2216 层 × ≈3.8 KB ✓）
- 修法（三层 ✓）：① **`renderMeasured` 改排队投递**（`Qt::QueuedConnection` + 合并 ✓ 状态栏只是诊断读数，稍后显示不影响功能 ✓）② **`paintEvent` 硬重入护栏**（RAII 深度计数 ✓ 已在绘制中就直接返回并写 `paint-nested` 面包屑 ✓✓ **无论触发者是谁都不再可能爆栈** ✓）③ **`ZoomBar` 滑条与百分比 pill 去掉悬停 tooltip** ✓（拖拽时鼠标就压在它们上面 ✓ 那正是 QToolTip 嵌套事件处理的策源地 ✓；提示改用 `statusTip`/可访问名 ✓ 不再弹窗 ✓）
- 回归锁：`smoke: paint never re-enters`（护栏确实生效、深度恒 ≤1 ✓）+ `smoke: render readout still arrives`（排队后状态栏照常更新 ✓）✓✓
- 经验：**① 绘制路径里绝不改 UI** ✓✓（改控件、改样式、弹 tooltip、重排都算 ✗）；**② 栈溢出用面包屑定位前，要先证明守卫覆盖了递归点** ✗ —— 本次三条面包屑全没写出来 ✓ 正是因为 `renderDepth` 只包住了 `m_doc->render()` 那一小段 ✓，**"该响的没响"本身就是强证据** ✓；**③ 没有 PDB 也能给原生崩溃定位** ✓✓：`.pdata` + 同源 DLL + 字符串字面量 + 栈上周期性重复 ✓（"周期帧数 / 栈跨度"就是互相递归的指纹 ✓）

**2.43 栈溢出的真凶（第三次，也是最后一次）：relayout 翻滚动条策略 → 尺寸反馈震荡**
- 关键转折：1.8.4 装到 VM 上**仍然崩、且是同一个偏移** `Qt6Widgets.dll+0xD4DBF` ✓，但日志里**没有 `paint-nested`** ✓ → 说明护栏没被触发 ✓ → **递归不经过 `PdfCanvas::paintEvent`** ✗（2.42 只对了一半 ✓）
- 工具升级：写了个"帧识别器" ✓ —— 用 **`.pdata` + 精确导出名匹配**给整环 42 帧命名 ✓✓（这次拿到了 `QWidgetPrivate::invalidateBackingStore_resizeHelper` ✓、`QWidgetPrivate::childAtRecursiveHelper` ✓、`QWidget::mapTo` ✓、`QWidget::shouldPaintOnScreen` ✓、`QApplicationPrivate::notify_helper` ✓、`QCoreApplication::notifyInternal2` ✓、`QMetaObject::activate` ✓、`QHighDpiScaling::roundScaleFactor` ✓、`user32` + `qwindows` ✓）
- 决定性一步：**反汇编 CI 构建的那份 exe**（= VM 上运行的同一二进制 ✓）✓✓ → 环上那个应用帧 `0x4345f` 正是 **`PdfCanvas::resizeEvent` 里 `call relayout()` 的返回地址** ✓✓✓（逐条对上：`QAbstractScrollArea::resizeEvent` → `invalidateRenders` → `relayout` → `if (m_toolbar) m_toolbar->reposition()` → `viewport()->update()` ✓）—— 也就是说 **VM 上那份 1.8.4 的 `resizeEvent` 里没有我的重入护栏 ✗**（护栏在 `paintEvent` 里 ✗）
- 根因：`relayout()` 结尾的 `setHorizontalScrollBarPolicy(maxHScroll > 0 ? AsNeeded : AlwaysOff)` ✓ → **改滚动条策略会让 `QAbstractScrollArea` 重排视口** → 触发 `resizeEvent` → 又 `relayout()` ✓；而 `maxHScroll` 依赖视口**宽**、`maxScroll` 依赖视口**高** ✓ → **水平/垂直两条滚动条互相翻转可见性 → 无限震荡** ✓✓✓（每圈还让后备存储失效 → 同步重绘 → 栈一路涨到 8 MB ✓）
- 修法：① **永不在 `relayout()` 里动滚动条策略**（只在构造时设一次 ✓ 隐藏的滚动条仍保有 range/value ✓ 双指平移照旧可用 ✓）② `relayout()` **深度上限护栏**（RAII + `relayout-nested` 面包屑 + **拒绝计数** ✓）③ **记忆化**：六个输入（文档/zoom/视口宽高/页数/最大页宽）没变就直接返回 ✓ —— 反馈环的重复请求本身变成空操作 ✓
- 回归锁：`smoke: relayout never nests`（深度恒 ≤4 ✓）+ 自测打印"**排版拒绝次数**"（本机 = **0** ✓ = 环消失而不是被压住 ✓）—— **1.8.5 装到那台教室 VM 上实测：狂拖缩放滑条不再复现 ✓、正式安装副本上全套自测 ALL PASS ✓、排版拒绝次数仍为 0 ✓**（250% DPI + 真实课件 ✓✓ 判决生效 ✓）
- 收尾时自测自己还暴露了一个问题 ✓：`showHomePage()` 不是 slot ✓，而自测用 `QMetaObject::invokeMethod(&window, "showHomePage")` 字符串调用 ✓ → **静默失败** ✗ → 紧随其后的「hidden on home」断言**永远为真** ✗（测试里出现"永远为真"的断言，正是本项目一直在防的那类错 ✓）。修法：把它标为 `Q_INVOKABLE` ✓ 并把三处 `invokeMethod` 的**返回值都变成断言** ✓✓ —— 名字对不上就立刻 FAIL ✓，不再有静默通过的断言 ✓。
- 经验：**① 布局函数必须是纯函数** ✓✓ —— 任何改变自身输入的动作（改策略、改约束、改可见性）都可能让布局函数自我递归 ✓；**② "崩溃偏移相同" ≠ "原因相同"** ✗ —— 前后两次是**同一个震荡**，但**环上抓到的应用帧不同** ✓，靠"哪些帧在环上"而不是"崩在哪一行"才定位到真因 ✓✓；**③ 有 CI 版 exe + 本机同源 Qt DLL，就能把原生崩溃精确映射回源码行** ✓✓

**2.45 橡皮环"卡在工具岛边缘、无法穿透"（浮层是鼠标事件的墙）**
- 现象（用户截图直给 ✓）：指针移到工具岛上时，橡皮环**冻在岛的边缘**不再跟随 ✓，越过之后又突然跳到另一侧 ✓ → "操作割裂" ✓

- 修法：加一个 **16ms 轮询全局光标**的 `trackPointer()` ✓✓ —— `QCursor::pos()` + `viewport()->mapFromGlobal()` 拿到真实位置 ✓：
  - 悬停：环继续跟随 ✓✓，因为岛是不透明的 ✓ 环只是**从岛后面穿过去**、在对侧重新出现 ✓✓ = 用户要的"穿透" ✓；指针在岛上时**恢复系统光标** ✓（否则空白光标让岛上按钮没法瞄准 ✓，规则收进 `applyToolCursor()` ✓）
  - 拖拽：继续喂 `moveInputTo()` ✓✓ → **鼠标橡皮/画笔能擦到、画到岛后面的内容** ✓（之前只有**触摸**路径做到这件事 ✓ —— 见 `touchBelongsToOverlay` + 手写事件转发 ✓）
  - 空闲即返回 ✓（一次查询两次比较 ✓）；触控与压感不受影响 ✓（`QGuiApplication::mouseButtons() == Qt::NoButton` 时拖拽分支直接返回 ✓ 它们有自己的跟踪路径 ✓）
- ⚠️ 诚实记账：这一条**没有自动化测试** ✗ —— 它需要真实的全局光标位置 ✓，`--selftest-image` 的无头环境给不出可靠结果 ✓ → 由用户在 VM 上手工验证 ✓（自测里唯一能锁的是"环的画法与导出隔离" ✓ 那两条仍在跑 ✓）
- 教训：**"浮层是子控件" ⇒ 它同时是一堵鼠标事件的墙** ✓✓ —— 任何需要在浮层上"穿过去"的交互，都必须自己用全局坐标跟踪 ✓（本项目在**触摸**路径早就遇到过同一问题并解决了 ✓，这次补齐**鼠标**路径 ✓ —— **同一个问题在不同输入路径上要各修一次** ✓）

## 3. 经验总结

1. **确定性自测 > 手点测试**。抓到的两个最隐蔽的 bug（撤销快照被改写、稀疏笔迹丢段）都来自程序化断言，而不是点击。
2. **真机验证不可替代**。红外触控、双指手势、DPI、任务栏遮挡等问题只在真实环境暴露。
3. **触摸输入会被"同时"当成鼠标**。在 Windows 上锁住一条路径是不够的。
4. **浮层不要用顶层窗口**。否则系统阴影、事件投递、关闭判定都会出问题。
5. **委托给 AI 也要验货**。Agent 会给出漂亮的完成汇报，但磁盘上可能什么都没有；核对文件、构建、测试是必须动作。
6. **约束先量化再设计**。把"8 GB / 4K / 红外触控"翻译成"31.6 MiB 一张全屏位图""`pointerType` 是 touch""原生手势不可用"，架构选择就自然清晰了。
