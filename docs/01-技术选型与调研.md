# 技术选型与调研

> 这份文档记录"为什么这么选"以及支撑结论的**实测数据与出处**。目标是让后来者能复核，而不是照抄结论。

## 0. 约束条件（决定了几乎所有取舍）

| 编号 | 约束 | 说明 |
|---|---|---|
| C1 | **8 GB 内存** | 目标一体机只有 8 GB，且被系统/iGPU 共享显存占用，是**最紧的一块板** |
| C2 | **4K 屏** | 单个全屏 RGBA 后备存储约 31.6 MiB，是内存的主要消耗项 |
| C3 | **低功耗 CPU** | 栅格化预算有限，不能整页高分辨率预渲染 |
| C4 | **Windows 10/11** | 一体机 Windows OPS 模块 |
| C5 | **红外触控 + 被动笔** | 笔被系统识别为**普通触摸**：无压感、无悬停、无独立笔 HID |
| C6 | 多文档 | 需要同时打开多个 PDF |
| C7 | 静默部署 | 教室批量下发（可通过集中管理客户端静默安装） |

## 1. 运行时选型：为什么不用 Chromium

| 方案 | 结论 | 关键证据 |
|---|---|---|
| Electron | ❌ 否决 | 空载基线 450–570 MB |
| **WebView2 / Tauri** | ❌ **否决** | 微软官方口径：**首个 WebView2 约 250 MB，每多一个文档再 +100 MB** → 3 个文档约 450 MB；且 `--single-process` **官方明确不支持**（稳定/安全风险） |
| pdf.js（纯 Web） | ❌ 否决 | 整页全分辨率画布、无瓦片；大尺寸扫描件实测可达数 GB 峰值 |
| WinUI 3 / Flutter | ❌ 否决 | WinUI 空窗 45 MB+、复杂应用 155 MB 量级；Flutter Skia ~100 MB、Impeller ~450 MB |
| **原生桌面** | ✅ **采用** | Qt **Widgets** 空载实测仅 ~4 MB（真实应用 22–57 MB）；`QML` 才是重的那个（空载 13 MB、真实应用 155 MB） |

**结论**：把运行时从"浏览器引擎 + 多进程"换成**单进程原生**，是把基线从数百 MB 压到几十 MB 的唯一途径。

## 2. PDF 引擎选型

| 引擎 | 许可 | 取舍 |
|---|---|---|
| **PDFium** | **BSD-3-Clause** | ✅ 采用。支持**视口裁剪渲染**（`FPDF_RenderPageBitmapWithMatrix`）与渐进渲染；位图恒 4 B/px；巨图有内部上限保护 |
| MuPDF | AGPL-3.0 | 扫描件更强（DCT 域 1/2、1/4、1/8 降采样解码；store 上限可配），但 **AGPL** 对闭源/混合分发不友好 |
| pdf.js | Apache-2.0 | Web 场景可用；整页渲染模型不适合本项目 |

**结论**：PDFium（许可干净、API 提供视口裁剪），并通过 Qt 的 PDF 模块使用。

## 3. 内存与 4K 的硬算术

后备存储恒为 `宽 × 高 × 4 字节`：

| 表面 | 字节 | MiB |
|---|---:|---:|
| 3840×2160（4K, DPR 1.0） | 33,177,600 | **31.6** |
| 4K @ DPR 1.5（5760×3240） | 74,649,600 | **71.2** |
| 4K @ DPR 2.0（7680×4320） | 132,710,400 | **126.6** |
| A4 @ 300 DPI | 34,800,000 | 33.2 |
| **512×512 瓦片** | 1,048,576 | **1.0** |

**推论**：DPR 是平方级放大器（1.5 → 2.25×，2.0 → 4×）。因此：**量化 DPR、只渲染可见区域、缓存按字节设上限**。

### 实测（本项目在目标机型上）

| 指标 | 实测 |
|---|---|
| 进程基线（`--bench`，仅 Qt + PDFium） | **24–27 MB** |
| 打开 4 页真实教材并渲染 | 25–27 MB |
| 双文档打开（多标签） | ~91 MB |
| 单页渲染（A4，约 1.1 MP） | 16–24 ms（首帧 50–60 ms） |

## 4. 输入：红外触控的现实

行业标准（T/CVIA 107-2023）把"**手 / 被动笔**"与"**主动电容笔**"分成两张独立性能表：只有后者有压感指标。红外屏的笔本质是"挡住红外光栅的物体"，因此：

- `pointerType` 是 **`touch`**（与手指无法区分）
- **无压力、无倾斜、无悬停**
- 系统级拒掌依赖"笔在感应范围内则取消触摸"这一机制 —— 红外屏**没有独立笔设备**，因此该机制不可用

**结论**：不能围绕压感设计；拒掌、笔/指区分必须在应用层自己解决，并且**双指手势必须与书写互斥**。

## 5. 交互与手势的踩坑结论

- Windows 上双指捏合**不一定**产生原生命中手势（红外屏、转发式触摸常见）。可靠做法是**直接读取多点触摸事件**（触摸点距离算缩放比、中点位移算平移）。
- 只要画布接受了触摸事件，**落在浮层上的触摸也会先到画布**（因为浮层子控件不接收触摸）。因此：
  - 浮层必须显式拦截/忽略这些事件；
  - 浮层的"点外部关闭"判定必须用**事件坐标**，不能用"事件投递给了哪个控件"。

## 6. 内存策略（最终采用）

| 策略 | 取值 |
|---|---|
| 渲染粒度 | **整页位图**（不做瓦片；在 200 MB 预算内整页 + 有界缓存足够） |
| 页缓存 | **LRU，上限 128 MB**，绝不淘汰可见页 |
| 单页保护 | 单页位图 > 100 MB 自动降采样 |
| 多文档 | 切换标签时释放非活动文档的位图（`releaseCachedPages()`） |
| 缩放中 | **不失效缓存**，直接拉伸已有位图绘制；手势停止 160 ms 后再重渲清晰版 |

> 瓦片化的触发条件（当前不做）：若将来必须在 **4K@100% 且同时缓存多页**时仍不掉帧，再升级为 512² 瓦片（1 MiB/张）。
